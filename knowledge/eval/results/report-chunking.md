# Chunking 横评与霸榜治理报告（单元 3.3）

> 日期：2026-11-13 · 分支 feat/kb · 口径：BGE-M3（unit 3.1）· GT：span 换算（unit 3.2 资产）
> 实验产物：`knowledge/eval/local/chunking_exp/`（gitignored，可再生）；本报告与两个实验脚本入库。

## 1. 实验设置

四方案在同一清洗语料上重切（`_chunk_body` 参数化，默认行为逐字不变），全部用本地 BGE-M3 重嵌（零 API 成本，四方案共约 90 秒），143 条 dev query 的向量跨方案共享，内存 cosine 检索（与 Qdrant cosine 距离口径一致——win800 臂 docR@10 = 79.7% 与 v7 Qdrant 基线完全吻合，口径对齐验证通过）。

**GT 换算**：suite 的 chunk 级 GT 焊死在 800/120 切分上（源 chunk id），换切分即失效。本实验用 unit 3.2 的 span 资产（doc 级坐标，与切分无关）换算每方案的 GT：

- **strict**：chunk 完整包含 ≥1 个答案 span（与 v7 源 chunk GT 语义等价）；span 被切分斩断且无任何完整包含者的 query 剔除出分母（empty GT，单独报告）
- **lenient**：chunk 与 span 有字符交集即可（更宽松的参考口径）

## 2. 四方案结果

| 方案 | chunks | span 完整率 | docR@10 | chunkR@10 (strict) | chunkR@10 (lenient) | empty GT |
|---|---|---|---|---|---|---|
| **win800_120（现状）** | 3255 | **96.3%** | **79.7%** | **55.0%** | 55.0% | 3 |
| win400_60 | 6400 | 92.7% | 68.5% | 43.7% | 42.1% | 8 |
| win400_0 | 5373 | 87.4% | 72.0% | 47.7% | 47.1% | 13 |
| para600（段落聚合 ~600） | 3389 | 84.8% | 74.8% | 48.5% | 48.6% | 7 |

**结论：现状 800/120 全面最优，切分不是杠杆。**

三个反直觉发现：

1. **「答案占比稀释」假设被证伪**。3.2 发现答案 span 中位数只占 chunk 的 10.6%，机制上预测小 chunk（占比翻倍）应提升 chunkR——实际 400 字方案 chunkR 暴跌 11.3pp，docR 也跌 11.2pp。解释：**BGE-M3（8K 上下文模型）对完整论述的表征质量远高于碎块**——800 字滑窗以句界下刀，块内是完整语义单元；400 字切碎论述后，正确 doc 的所有 chunk 语义质量整体下降，被其他 doc 的完整块反超（docR 同步大跌证实这是全局效应而非 top10 内排序抖动）。3.2 报告里对发现 2 保留了「风险度量、不必然损失」的定性，本实验完成因果裁决：稀释压力存在但模型扛得住，**语义完整性 > 答案占比**。
2. **overlap 在 800 尺度下几乎无用（3.2：仅保护 2.3% span），在 400 尺度下开始有保护价值**（400/60 完整率 92.7% vs 400/0 87.4%，差 5.3pp）——切点数量翻倍后撞上 span 的概率上升。但这救不了 400 方案的检索劣势。
3. **para600 淘汰且带实现缺陷**：span 完整率最低（84.8%）。miss 模式：63 条为 span 尾部跨块 flush 点溢出（溢出 20-80 字——聚合块边界落在段落起点，与标注 span 的端点分布不匹配），13 条为块覆盖空洞（para 实现的正文覆盖 bug）。段落边界是「语义上干净」的切点，但答案 span 不尊重它。

## 3. doc 霸榜治理（per-doc 限额重排）

在 win800 上检索 top-50 → 贪心 per-doc 限额重排（每 doc 最多 quota 条进 top10，纯索引层零成本）：

| 策略 | docR@10 | chunkR@10 |
|---|---|---|
| 无限额（基线） | 79.7% | 55.0% |
| quota=3/doc | 81.8% | **55.7%** |
| quota=2/doc | 82.5% | 52.9% |
| quota=1/doc | **88.1%** | 44.3% |

**docR 与 chunkR 在 quota 上是跷跷板**。quota=1 让 doc 覆盖最大化（+8.4pp）但正确 doc 内的第二/第三名 chunk（含答案的）被挤出——chunkR 崩 10.7pp。本产品检索结果直接拼 generation prompt，**chunkR 是主指标**，quota=1 不可取。quota=3 是唯一双赢点（docR +2.1pp / chunkR +0.7pp，免费），但收益微弱且改变检索行为语义——**不进主链路**，3.5 重跑时作为可选项对比，若 trap/对抗场景需要 doc 多样性再启用。

## 4. 失败 case 归因（34 条 doc-hit & chunk-miss）

win800 下 34 条「doc 命中但 chunk 未命中」，按 top10 内同 doc chunk 结构分类：

- **同 doc 兄弟挤占 16/34（47%）**：正确 doc 的 intro/结论类概括块（「主题海绵」，与 query 整体主题相似度高但不含具体答案）占满 top10，含答案的具体块排 11+。极端 case 10 条全同 doc。
- **孤军型 13/34（38%）**：正确 doc 只挤进 1 条（不含答案），其余被外 doc 占据——跨 doc 语义竞争失败（其他 doc 的泛主题块更贴 query 词面）。
- **双 doc 名额挤占 5/34（15%）**：multi_context 双 doc 需求，第二 gt doc 命中但第一 gt doc（含 span）被挤出。

典型 case 的深层模式（人工读 span 原文 vs 错误块原文）：**跨语言鸿沟**（中文 query 找英文原文，syn021/065/082）、**代码-自然语言鸿沟**（答案在代码片段，syn085）、**概括块 vs 细节块的区分失败**（syn018/076）。

**全部 34 条都是排序问题，零条与切分有关**（span 完整率 96.3% 已说明物理保护接近上限）。

## 5. 裁决与影响

1. **切分固化 800/120**（即维持现状，build_kb 无需改动）——四方案横评全面最优 + 双指标依据完备。
2. **优化主战线从「切分」正式转向「排序」**：3.7 chunk 级 rerank（bge-reranker-v2-m3）优先级上调——它是对「同 doc 兄弟挤占」与「概括块 vs 细节块」唯一对症的方向（cross-encoder 细粒度交叉注意力天然区分「主题相关」与「含答案」）。
3. **3.4/3.5 的快照重建不受切分影响**：span 资产直接复用，suite 的 chunk 级 GT 继续按 800/120 有效。
4. quota=3 作为一个免费微增益留档，不进主链路。

## 6. 方法论备注

- 本实验是「假设驱动被证伪」的样本：3.2 的稀释机制链（占比小 → 向量被稀释 → 排序差）在直觉上自洽、在 BGE-M3 上不成立。负向结果的价值：避免在切分参数上继续投入（否则 3.7 rerank 的窗口会被延误），并产出了「语义完整性 > 答案占比」这一可迁移结论。
- chunk 级 GT 与切分耦合的问题由 span 资产彻底解决：四方案 × 143 query 的评估未产生任何标注成本。
