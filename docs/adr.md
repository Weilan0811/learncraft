# 架构决策记录（ADR）

## ADR-001 互动讲义使用 Composer 生成受限 HTML

**背景**：完全自由生成 HTML 容易版式趋同、样式失控；预先定义复杂组件又容易机械、呆板。

**决策**：教学大纲与单元规格负责“教什么、怎么互动”，Composer 只负责把单元规格渲染为受限 HTML 片段与作用域 CSS；外壳、导航、样式容器、交互运行时由前端统一提供，HTML 经 DOMPurify 白名单清洗。

**结果**：章节内容可以自由表达，交互和视觉基线保持稳定；新增教学块只需扩展规格与运行时动作。

## ADR-002 多章节并行生成、逐单元落库

**背景**：一次性生成整篇内容耗时长，失败会整体重来。

**决策**：大纲确定后并行生成单元，每个单元完成立即写入 `unit_render` 并推送事件；最终再组装 `final_render`。

**结果**：首屏更快、生成过程可见；单单元失败可单独重试或降级，不阻塞其它章节。

## ADR-003 学习数据持久化，单引擎双仓储

**背景**：学习会话最初是内存实现，进程重启即丢失，无法支撑摘要与再生成。

**决策**：新增 `interactive_learning_session` 与 `interactive_learning_event` 两张表；学习仓储复用任务仓储的 `Engine`，不重复建连接池，也不重复执行迁移。

**结果**：会话可跨重启读取；运行时只有一个连接池；测试通过注入临时 SQLite engine 隔离数据。

## ADR-004 离线讲义保留答题记录

**背景**：学生需要把互动课保存下来复习，平台也需要可归档的学习凭证。

**决策**：导出 HTML 时要求 `session_id`，保留在线讲义外壳与章节内容，移除交互控件，并在每章追加学生回答、对错、参考答案与引用。

**结果**：导出文件既能复习又能作为学习记录；没有会话时导出会明确报错，避免生成“看似完整但没有学习数据”的讲义。

## ADR-005 adaptive brief 先用规则与模板

**背景**：理想的 brief 应由 LLM 结合学生画像生成，但当前需要先闭环、可测试、可解释。

**决策**：摘要与 brief 先用确定性规则：正确率、求助次数、薄弱概念、复习章节、建议难度；响应结构按 LLM 版本设计。

**结果**：闭环稳定、结果可复现、测试成本低；后续只需替换 `AdaptiveBriefService.build` 的内部实现，前端与平台契约不变。

## ADR-006 摘要只出现在互动讲义预览

**背景**：摘要是学习行为的结果，不应干扰其它内容类型的生成流程，也不应出现在离线导出或历史记录中。

**决策**：摘要面板由 `InteractiveHtmlRenderer` 自身渲染，仅当会话已有答题时出现；“针对薄弱点再生成”只在同一位置提供。

**结果**：入口唯一、语义清晰；其它内容类型不需要感知学习闭环。
