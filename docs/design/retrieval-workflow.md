# 大纲与章节生成前的知识查询

## 片段身份、索引构建与来源记录

片段编号采用`文档ID::section-章节位置::chunk-片段序号`。同名章节的不同位置不会共用编号，标题仍作为检索元数据。编号属于第二版格式，构建时间与格式版本保存在`storage/kb/meta.json`。

`python -m knowledge.scripts.build_kb --rebuild`先在独立目录构建并验证BM25和向量索引，再替换当前索引，保留旧目录备份；替换前需要停止使用当前知识库的服务。构建失败不会删除当前索引。替换文件时发生异常会恢复原目录。

如需只构建而不替换，使用`python -m knowledge.scripts.build_kb --rebuild --output-dir storage/kb-candidate`，输出目录必须为空。向量模型、过滤规则、切分尺寸与融合配置继续沿用已有设置。

旧实验保留原快照；数据库原有正文缓存编号保持原样。新的检索记录独立保存检索编号、完整正文、文档内位置、索引元数据，以及生成节点实际看到的前500字符。位置以引擎清理后的文档正文为基准。

同进程的BGE-M3实例共用已加载权重，避免大纲与并发章节重复加载模型。

## 大纲校验与一次修复

大纲校验统一检查章节数上限、类型、序号、有效查询和引用。`units.source_chunk_ids`及`sections.citations`都只能使用本次大纲检索提供的片段编号。有资料时，缺少章节引用仍为错误。

校验通过后才发送`outline_ready`事件。首次校验失败后可执行一次大纲修复，再次校验仍未通过则任务失败，不发送大纲可用事件。修复沿用已有LLM服务，其结构修复和网络重试另有记录，因此一次逻辑修复可能包含多次实际HTTP请求。

修复提示只提供本次资料、原大纲、学生请求及校验错误。资料不足时，模型可在`metadata.insufficient_knowledge`中说明缺少的知识；这类输出保持未通过状态。不能用任意有效编号代替真正的依据。

修复次数沿用工作流的`retry_counts`，错误、耗时与用量保存到大纲`metadata.validation_repair`。检索及阶段用量依据通过下述任务产物保存，数据库表结构不变。

模型用量在实际执行调用的线程中收集：查询规划保存在`query_planning.model_calls`，大纲生成保存在`metadata.generation.model_calls`，大纲修复保存在`metadata.validation_repair.model_calls`，章节调用保存在对应`retrieval_record.model_calls`。包含结构修复产生的成功响应；没有返回用量的请求仍需以服务商账单核对。索引增删会更新元数据的`updated_at`。

## 运行方式

启用本地知识库（`CONTENT_GENERATOR_KB_PROVIDER=local`）时，流程如下：

1. 根据用户主题、需求、内容类型和生成参数，调用文本模型规划1至4条知识查询。每条查询包含查询文本和用途说明，覆盖任务所需的核心知识、必要背景和适当拓展。
2. 逐条执行查询，按排名合并相同片段，向大纲模型提供检索资料。
3. 大纲模型为每章输出 `retrieval_queries`（后续需要查证或补充的知识请求）。
4. 每章生成 spec（内容规格）前，逐条执行这些请求。查询文本不再附加整课任务、章节核心信息或程序阶段标记。各章仍可以并发执行。
5. 根据本章检索资料生成 spec。若本章检索没有返回资料，沿用原有的大纲阶段资料，并明确记录使用情况。

当前采用一次大纲查询规划、一次检索执行的方式。章节阶段直接执行大纲提供的请求，不额外调用模型重新规划查询。未实现模型根据结果连续追加查询的多轮流程。

本地知识库关闭时，沿用无检索生成流程，不增加查询规划调用。新流程使用项目配置的文本服务和模型，增加一次逻辑上的查询规划调用；结构修复及网络重试仍遵循文本服务的现有处理方式。

## 代码与提示词

- `backend/app/workflows/nodes/retriever_node.py`：查询规划、执行与工作流状态更新。
- `backend/app/prompts/retrieval/planning_queries.md`：大纲前的查询规划提示。
- `backend/app/schemas/retrieval.py`：查询文本与用途说明的结构要求。
- `backend/app/services/local_kb_service.py`：接收显式查询列表，逐条检索并使用等权RRF（根据各查询中的名次累加得分）合并结果。
- 大纲提示位于 `backend/app/prompts/planner/`，明确要求章节查询可以独立执行。

直接调用 `LocalKBService.retrieve()` 时，可通过 `queries=[...]` 提供精确查询。未提供此参数的调用仍使用原规则拼接方式，可用于已有命令与规则查询对照；工作流在知识库启用时始终传入显式查询。

本次修复查询的生成与执行流程，保留原有片段索引、向量前缀、关键词与向量融合方式及返回数量，避免把流程修复与检索参数调整混为一次效果变化。

## 保存的记录

工作流状态包含：

- `planning_query_plan`：大纲前模型提出的查询及用途。
- `retrieval_records`：每个阶段实际执行的查询、每条查询的状态和片段编号、本章是否采用大纲阶段资料。
- 每个返回片段的 `metadata.matched_queries`：哪些查询找到了它。

任务保存时，将查询规划写为 `retrieval_plan` 记录，将大纲和各章的查询执行结果写为 `retrieval_record` 记录。各章并发完成后的合并和中间保存均包含这些记录。无返回结果的查询也能被追踪。

查询规划记录包含耗时和最后一次模型响应的用量。若发生格式修复或重试，分析总调用成本应使用现有的逐调用指标，不能只累加最后一次响应。

## 评价需要区分两个问题

### 课程知识准备是否合适

输入应是学习目标、受众、深度和约束。先制定不依赖候选模型输出的需求清单，区分核心知识、必要背景和可选拓展，再评估查询计划及检索资料对这些需求的覆盖、无关材料比例和成本。已知来源可以帮助核查，但不限制其他有效材料。

最终的大纲与章节是否准确、完整、适合受众，需要单独评价，不能用检索命中率代替。

### 具体查询是否执行有效

保存模型当时的查询文本及用途，判断找回的片段能否支持其信息需求。查询需要的资料在库中不存在、查询表达不清和检索没有找回已有资料，应分别记录。

多个查询的结果合并后，还要检查必要的背景或细节是否被其他查询的重复材料挤出。相关性候选应合并所有参评检索方法的结果，未知片段不自动标为不相关。

## 评价数据的使用范围

查询规划评价使用学生自学请求、独立制定的课程知识需求和人工审核意见。检索评价另外保留模型实际提出的查询、用途及相关片段标注，分别检查课程支持程度与具体查询的执行效果。

基于目标片段生成的问题适合检索回归和案例分析；不能仅凭这类数据评价查询规划对真实学习需求的覆盖。比较不同策略时，应固定语料与索引，记录全部实际调用、耗时和费用，并单独评价最终内容质量。特定语料上的实验结果不作为任意材料上的效果保证。
